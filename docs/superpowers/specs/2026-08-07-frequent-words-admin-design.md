# สเป็กหน้า “คำที่ใช้บ่อย” สำหรับ Admin

สถานะ: ผู้ใช้อนุมัติแนวทางและ UX แล้ว เมื่อวันที่ 2026-08-07

## เป้าหมาย

เพิ่มหน้าจัดการคำที่ใช้ในช่อง `datalist` ของหน้า Admin เพื่อให้ผู้ใช้เพิ่ม แก้ไข และลบคำได้จากหน้าเว็บ โดยข้อมูลการเปลี่ยนแปลงต้องถูกบันทึกกลับ Google Sheets และสะท้อนกับคิวเดิมที่เกี่ยวข้อง

## ขอบเขต

ครอบคลุมตัวเลือก 6 กลุ่ม:

- `Diagnosis`
- `Operation`
- `Surgeon`
- `Anesthetist`
- `สิทธิ์การรักษา`
- `ประเภทการผ่าตัด`

การเปลี่ยนแปลงใน `DatalistOptions` เป็นระดับทั้ง row:

- แก้ไข: เปลี่ยนเฉพาะ `value` และ `normalizedKey` ใน row เดิม โดยคง `type` และ `createdAt` เดิมไว้
- ลบ: ลบ row ของคำออกจากชีตจริง
- หากค่าใหม่มี `normalizedKey` ซ้ำกับ row อื่นในกลุ่มเดียวกัน ให้ปฏิเสธการแก้ไขและคงข้อมูลเดิมไว้

การเปลี่ยนแปลงใน `Queues` เป็นระดับช่องข้อมูล:

- แก้ไขคำ: แทนที่คำเดิมในทุก row ที่เป็นกลุ่มเดียวกัน
- ลบคำ: ล้างเฉพาะช่องที่มีคำนั้น ไม่ลบทั้ง row ของคิว
- สำหรับ `surgeryType`: แก้ไขหรือเอาค่าออกจาก JSON array โดยคงค่าประเภทอื่นไว้

ไม่เปลี่ยน schema ของ `Queues` หรือ `DatalistOptions` และไม่เพิ่ม dependency ใหม่

## ทิศทาง UI

คง visual system และ responsive pattern ปัจจุบันของ `Admin.html` ซึ่งเป็นหน้าเครื่องมือปฏิบัติงานโทนสว่าง ใช้สีหลัก น้ำเงิน ฟอนต์ Sarabun/Outfit ปุ่มเดิม และขนาดพื้นที่สัมผัสอย่างน้อย 44px

### Desktop

คงพื้นที่เพิ่มคิวและรายการคิวเดิมไว้ แล้วเพิ่ม panel ใหม่ชื่อ `คำที่ใช้บ่อย` เต็มความกว้างใต้พื้นที่เดิม เพื่อไม่บีบฟอร์มหรือตารางให้แคบลง

Panel ประกอบด้วย:

1. หัวข้อและคำอธิบายสั้น
2. ฟอร์มเพิ่มคำใหม่: เลือกกลุ่มและกรอกคำ
3. แสดงรายการเฉพาะคำของกลุ่มที่เลือก โดยมีคอลัมน์คำ วันที่สร้าง และปุ่มแก้ไข/ลบ
4. สถานะ loading, empty และ error

การแก้ไขใช้ inline row พร้อมปุ่มบันทึกและยกเลิก การลบต้องมี confirmation ก่อนส่งคำสั่งไป server

### iPad และมือถือ

เพิ่มเมนูบาร์ด้านล่างเป็น 3 หน้า:

1. `เพิ่ม/แก้ไขคิว`
2. `รายการคิว`
3. `คำที่ใช้บ่อย`

เมื่อเลือกหน้าที่ 3 ให้ซ่อน panel เดิมและแสดง panel คำที่ใช้บ่อยเต็มพื้นที่ เนื้อหารายการปรับจากตารางเป็นการ์ดเมื่อหน้าจอแคบ เพื่อหลีกเลี่ยง horizontal overflow

## Data flow และ API

คง `getDatalistOptions()` ไว้สำหรับโหลดค่าไปเติมช่อง `datalist` ในฟอร์มเดิม และเพิ่ม API สำหรับหน้าใหม่ดังนี้:

- `getDatalistEntries()` คืน row ที่ปลอดภัยสำหรับแสดงผล โดยมี `type`, `value`, `normalizedKey` และ `createdAt`
- `createDatalistOption({ type, value })` เพิ่ม row ใหม่ใน `DatalistOptions` โดยไม่สร้างคิว
- `updateDatalistOption({ type, normalizedKey, value })` แก้ row และ sync ข้อมูลคิวเดิม
- `deleteDatalistOption({ type, normalizedKey })` ลบ row และ sync ข้อมูลคิวเดิม

คำสั่งแก้ไข/ลบต้องใช้ `LockService.getScriptLock()` เหมือน mutation เดิม ตรวจกลุ่มคำที่อนุญาต ตรวจค่าที่ไม่ว่าง และหา row ด้วย `type + normalizedKey` หลัง normalize ช่องว่างและตัวพิมพ์ตามกติกาเดิม

ทุก mutation ต้องทำงานเป็นชุดเดียวภายใต้ lock:

1. อ่านและตรวจ row ต้นทาง
2. หากเป็นการเพิ่ม ให้ตรวจซ้ำแล้วเพิ่ม row ใน `DatalistOptions`
3. หากเป็นการแก้ไขหรือลบ ให้แก้ไขหรือลบ row ใน `DatalistOptions`
4. หากเป็นการแก้ไขหรือลบ ให้แก้ไขหรือล้าง field ที่เกี่ยวข้องใน `Queues`
5. ล้าง cache รายการคิววันนี้เมื่อมีการเปลี่ยน `Queues`
6. คืนผลลัพธ์พร้อมจำนวน row ตัวเลือกและ row คิวที่ได้รับผลกระทบ

หากเกิดข้อผิดพลาดระหว่างชุดคำสั่ง ต้องคืน `{ ok: false, error }` และไม่แสดงข้อความสำเร็จบนหน้าเว็บ

## กติกาการจับคู่ข้อมูล

- คำ scalar (`diagnosis`, `operation`, `surgeon`, `anesthetist`, `rights`) จับคู่ด้วย `type` และค่า normalized เดิม
- การแก้ไขใช้ค่าใหม่ที่ trim และรวมช่องว่างแล้วเขียนลง field ของคิวทุก row ที่จับคู่ได้
- การลบ scalar เขียนค่าว่างลง field ที่จับคู่ได้
- `surgeryTypes` parse เป็น array; แก้ไขแทนที่ค่าเดิมใน array และลบเอาค่าเดิมออกจาก array
- การแก้ไขที่ชนกับ normalized key เดิมในกลุ่มเดียวกันถูกปฏิเสธพร้อม error สำหรับผู้ใช้ ไม่ merge และไม่เปลี่ยนข้อมูลคิว

## สถานะและการเข้าถึง

- ปุ่มแก้ไข ลบ บันทึก และยกเลิกต้องเป็น semantic button และมี accessible name
- ปุ่มลบใช้สถานะ destructive และต้องยืนยันก่อนทำงาน
- ระหว่าง mutation ปิดปุ่มของ row นั้นเพื่อป้องกันการส่งซ้ำ
- สำเร็จให้แสดง toast พร้อมจำนวนข้อมูลที่ปรับ เช่น จำนวน row ในชีตและจำนวนคิวที่ sync
- toast สำเร็จหายอัตโนมัติหลัง 3.5 วินาที, ข้อความทั่วไปหลัง 4.5 วินาที และข้อผิดพลาดหลัง 6 วินาที โดยข้อความใหม่ยกเลิก timer เดิม
- ผิดพลาดให้คงข้อมูลที่ผู้ใช้กรอกไว้ และแสดงวิธีลองใหม่
- รองรับ focus-visible, forced colors และ `prefers-reduced-motion` ตามกติกาเดิม

## การทดสอบและการตรวจรับ

ฝั่ง backend ต้องมี regression test สำหรับ:

- แก้ไข row ของ `DatalistOptions` และคำนวณ `normalizedKey` ใหม่
- ลบ row ของ `DatalistOptions`
- sync ค่า scalar ใน `Queues`
- sync ค่า `surgeryTypes` แบบ JSON array
- ไม่ลบ row ของ `Queues` และคืนจำนวนผลกระทบที่ถูกต้อง
- ปฏิเสธกลุ่มที่ไม่อนุญาต ค่าว่าง และคำซ้ำ

ฝั่ง Admin ต้องมี regression test สำหรับ:

- มี panel และแท็บที่ 3 ชื่อ `คำที่ใช้บ่อย`
- โหลด row แล้วกรองแสดงเฉพาะรายการของกลุ่มที่เลือกจาก dropdown เดิม โดยไม่เพิ่มตัวกรองซ้ำ
- ส่ง payload แก้ไข/ลบที่ถูกต้อง
- refresh datalist หลัง mutation สำเร็จ
- แสดง error และยกเลิกการบันทึกเมื่อ server ไม่สำเร็จ

ก่อนส่งมอบให้รันชุดทดสอบที่เกี่ยวข้อง, `node tests/run-all-tests.mjs` หากสภาพแวดล้อมรองรับ, `git diff --check` และตรวจ Desktop 1440px, iPad 1024px และมือถือ 390px โดยเฉพาะเมนูบาร์ 3 หน้าและการไม่เกิด horizontal overflow
